{# ==================== QUICK START ==================== #}

Quick start

Your first workflow in five steps.

1
Create a chain

Chains → New chain. Give it a name (e.g. "ICT Standard") and a lowercase code (e.g. ict-standard).

2
Add steps

Inside the chain, click Add step. Each step says who acts and what they do. Reorder by dragging the handle or using the ▲▼ arrows.

3
Create a request type

This is what users pick when raising a request. It links a category, a handling office, and a chain together.

4
Test it

Use the Resolution tester to see the exact chain a specific request would follow. Do this before switching it on.

5
Switch it on

Set the request type to Active. New requests will use it immediately. Existing in-flight requests finish on their current chain.

{# ==================== CONCEPTS ==================== #}

Five concepts

The vocabulary everything else is built on.

1

Chain

A named, ordered sequence of steps. Examples: ict-standard, hr-leave, fleet-trip. One chain can serve many request types.

2

Step

One stage. Has a kind (approval / assignment / fulfillment / closure), an approver (who acts), and a scope (which department).

3

Request type

The kind of thing a user raises: "Broken computer", "Vehicle trip". Links a category and handling office to a chain.

4

Category

A theme grouping many types — ICT, Fleet, HR, Facilities. Organisational only; doesn't affect routing.

5

Runtime chain

The full sequence a specific request actually follows. Built at raise-time from the request type's chain + mandatory extras (Finance, Audit, HR, ES, Records) + the requester-side chain for cross-department types.

{# ==================== STEP KINDS ==================== #}

Step kinds

Four kinds. Every chain uses a mix.

Approval

Approves, returns, or rejects the request.

Actor: Resolved approver (role, head, director, or specific user).
Assignment

The acting user picks the staff member who will actually do the work.

Actor: Typically the receiving director.
Fulfillment

The assigned staff member marks the work done.

Actor: The assignee, not the approver.
Closure

The requester confirms receipt — this finalises the request.

Actor: The requester.
Always end on a closure step.

Without one, the request completes silently when the last approval passes — the requester won't get to confirm receipt.

{# ==================== APPROVER KINDS ==================== #}

Who acts at a step

Seven ways to resolve the actor. Pick one per step.

role_in_department

Any active user with the selected role in the selected scope's department.

requester_head

The most senior person in the requester's own department.

requester_deputy

The deputy director of the requester's department.

requester_director

The director of the requester's department.

receiving_director

The director of the handling department.

specific_user

One named user — always resolves to that person.

es

The Executive Secretary (role executive-secretary).

Scope picks the department.

requester = the requester's own. receiving = the handling office. Or a specific department code like finance, audit, hr.

{# ==================== MANDATORY VS HIERARCHICAL ==================== #}

Hierarchical vs mandatory

One checkbox. Big implications.

Hierarchical default — ON

Part of the normal chain. If the resolved actor is junior to the requester, the step is skipped automatically.

Use for: officer → head → deputy → director chains. The ES's request shouldn't bounce through an officer's desk.
Mandatory gate hierarchical OFF

Always runs. Rank doesn't matter. Even the Director's request goes through this step.

Use for: Finance, Audit, HR, ES sign-off, Records filing. Anything where compliance is the reason, not chain-of-command.
Rule of thumb:

If the step exists to enforce compliance, turn hierarchical OFF. If it exists to reflect chain-of-command, leave it ON.

{# ==================== CROSS-DEPARTMENT ==================== #}

Cross-department flow

When a request crosses between departments.

When is_cross_department is on and the requester and handling department differ, the runtime chain is assembled in three phases:

Phase 1
Requester's own chain

Their head, then their director approve the request internally first.

Phase 2
Mandatory extras

Finance, Audit, HR, ES, Records — whichever the request type requires.

Phase 3
Receiving chain

The handling department's own workflow: director approval, assignment, fulfillment, closure.

The handoff happens when Phase 1 finishes. The request then shows as "Awaiting receiving department" and pops into the receiving director's queue.

Config key controls the receiving chain's rank-skipping.

workflow.cross_dept_routing can be full_chain (default — untouched), rank_aware (rank-skipped too), or director_direct (directors skip junior steps; ES keeps full chain).

{# ==================== TESTING ==================== #}

Testing

Always run these four scenarios before you switch a chain on.

1
Typical requester

A regular officer raising the type. Confirm the full chain looks right.
2
A director as requester

Junior steps should be auto-skipped. If they aren't, the step's hierarchical flag is wrong.
3
An ES as requester

Confirm ES does not skip the receiving chain — that's intentional behaviour.
4
A cross-department type

Confirm the handoff marker lands on the right step and the extras run before the receiving chain.

The tester builds a preview request that is not saved. It's safe to run any number of times.

{# ==================== CHANGE SAFETY ==================== #}

Change safety

What happens to in-flight requests when you edit a chain.

In-flight requests keep their chain. Every request stores its current step identity (db:<pk> or syn:<name>) in its metadata. Editing the chain after the fact doesn't retroactively move the request.

Delete a step

In-flight requests skip it silently on their next advance. No error.

Reorder steps

Existing requests keep their current position. The engine doesn't re-sort them.

Add a step

In-flight requests hit it if it lands after their current position.

Deactivate a chain

In-flight requests finish normally. New requests of that type are blocked.

Making a material change? Create a new chain instead.

If you need to restructure a chain that's already processing requests, create a new chain and point the request type at it. Existing requests finish on the old chain, new ones use the new. Zero disruption.
